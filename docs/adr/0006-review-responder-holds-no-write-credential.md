# The Review responder's agent holds no write credential; a separate job pushes and speaks for it

The Review responder (`claude-review-response.yml`, #199) addresses a code review on a pull request: it fixes or declines each finding, and to prove a fix it has to build the pull request's code. Whatever runs in that job can therefore be reached by the pull request's own dependencies and build scripts, so the job is given nothing worth taking — a read-only job token and no `id-token` grant. The agent commits locally; its commits leave the runner as a git bundle. A `publish` job on a fresh runner, with only default-branch code checked out, validates the bundle, pushes it with the job token, starts the CI run GitHub holds for such a push, and replies on and resolves the review threads. "Only the implementer holds the Claude App token" stays true, and `scripts/ci-workflow-contract.test.mjs` still enforces it.

## Considered Options

- **Push from the agent's job as the Claude GitHub App, as `implement` does** — the first design, rejected after its security audit. `id-token: write` is a job-wide grant, so every step of that job, including `npm ci` and each `cargo` build of pull request code, could exchange it for a token that writes to the repository. The implementer avoids this only because it builds the default branch.
- **Keep the App token and install dependencies with scripts off** — rejected; the agent's own builds still run dependency code beside the grant. It narrows the exposure without closing it.
- **Push with the job token and dispatch CI on the branch** — rejected on evidence: checks from a `workflow_dispatch` run are recorded on the commit but do not appear in the pull request's checks and cannot satisfy a required check. A job-token push does create the ordinary `pull_request` CI run, held for approval; `publish` approves that run instead, for exactly the commit it pushed and for the CI workflow only.
- **Hand the commits over as patches (`git format-patch` / `git am`)** — rejected; applying a patch writes a working tree from attacker-written text and changes every commit id, so the agent's "fixed in <sha>" claims could no longer be checked. A bundle is fetched as objects, never checked out, and keeps the ids.
- **Let the agent reply and resolve itself with `gh api`** — rejected; `gh api` also reaches merging, branch deletion and labels, and the agent could resolve threads it was never given.
- **Auto mode by label, reusable workflow, or a review → respond → review loop** — a label applied with the job token starts no run; a reusable workflow would make the reviewer workflow hold the responder's permissions; and two agents from one model family converging on agreement is the failure to avoid. The reviewer's `handoff` job dispatches the responder, is the only job in that workflow holding `actions: write`, and stops after two rounds on a pull request. A response round never starts a review.

## Consequences

`publish` trusts nothing from the agent's runner. A round's commits are accepted only as a straight line of at most twenty ordinary commits on the commit the round started from, with no merge, symlink or submodule, touching no agent instruction file, no workflow file and no path that is unsafe to check out on Windows. A "fixed" verdict has to name one of the commits `publish` itself pushed, and the thread is resolved only if that commit changes the file the finding is on; a fix claimed elsewhere gets a reply and stays open. The summary comment carries no agent-written text, because its author and marker are what the round cap counts.

Rounds are refused on fork pull requests, on pull requests that do not target the default branch — "trusted code" here means the default branch's, and a pull request into any other branch would make that branch's author the trust root — on Dependabot pull requests, and on pull requests that change agent instruction files.

What remains exposed is the subscription token: the agent step has to hold it while pull request code builds. Dependency install scripts are off and the action's subprocess environment scrub is on, but the scrub is best-effort by its own description. That token can make model requests and nothing else, and is revoked by re-running `claude setup-token`.

On the label path the workflow file itself comes from the pull request's merge commit, as for every `pull_request` workflow here; that is the standing basis that anyone able to push a same-repository branch can already run an edited workflow with these secrets. The dispatch path names the default branch explicitly, because a dispatch runs the workflow file of whatever ref it is given.
